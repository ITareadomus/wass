Ecco la scaletta completa (end-to-end) per avere:

3 wave (EO, HP, LP) applicate con i pulsanti Assegna dei container

e un optimizer che, per HP e LP, costruisce assegnazioni intelligenti basandosi sulla timeline reale già popolata (inclusi i tuoi spostamenti manuali), senza usare daily_task_locks.

Idea guida: ogni wave è un commit non distruttivo in daily_assignments_current.
Le wave successive leggono la timeline come baseline e ottimizzano “attorno” a ciò che c’è già.

0) Definisci la regola (1 minuto)

Source of truth della timeline = daily_assignments_current

Dopo “Assegna EO”, quei task sono già in timeline.

Quando poi fai “Run HP”:

EO non va riassegnato (non entra tra i candidati),

ma EO deve essere letto come baseline (tempi occupati, ultimo punto, travel, straordinarie, ecc.)

Stessa cosa HP→LP.

Questo è esattamente “vedere ma non riassegnare”.

A) UI: 3 pulsanti “Assegna” (EO/HP/LP)
A1) Ogni pulsante chiama un endpoint “apply-wave”

Dove: frontend (container EO/HP/LP)

Assegna EO → POST /api/optimizer/apply-wave { runId, workDate, wave:"EO" }

Assegna HP → POST ... wave:"HP"

Assegna LP → POST ... wave:"LP"

Poi fai refresh timeline leggendo daily_assignments_current.

Non usare più “apply-to-production” monolitico.

B) Backend: apply-wave = commit incrementale NON distruttivo
B1) Aggiungi applyOptimizerWaveToProduction

Dove: server/services/optimizer/runAllPhases.ts (vicino a applyOptimizerToProduction)

Questa funzione deve:

prendere da optimizer.optimizer_assignment solo la wave richiesta

inserire in daily_assignments_current solo i task che non ci sono già

NON cancellare nulla

NON aggiornare righe già presenti (per non distruggere manual edits)

Regola chiave:

INSERT ... SELECT ... WHERE oa.run_id = runId AND oa.priority_type = wave

con NOT EXISTS su daily_assignments_current per evitare duplicati.

📌 Questo garantisce:

EO entra

HP aggiunge senza toccare EO/manuale

LP aggiunge senza toccare EO+HP/manuale

B2) Endpoint POST /api/optimizer/apply-wave

Dove: server/routes.ts

riceve runId, workDate, wave

chiama applyOptimizerWaveToProduction(...)

C) Rendere l’optimizer “wave-aware” (intelligente sulle wave precedenti)

Questo è il pezzo fondamentale: HP/LP devono leggere la timeline reale già costruita.

C1) Nuova query: leggi la baseline dalla timeline

Dove: server/services/optimizer/db.ts (aggiungi una funzione tipo)

loadTimelineBaseline(workDate) che ritorna:

per ogni cleaner_id:

lista task già in daily_assignments_current ordinati (sequence/start_time)

(minimo) ultimo task: end_time + posizione (lat/lng o logistic_code)

(meglio) tutti i segmenti: start/end per eventuali gap

Questa funzione NON tocca straordinarie: le straordinarie si calcolano poi sul totale.

C2) Input candidates: i task già in timeline NON sono candidati, ma sono contesto

Dove: server/services/optimizer/db.ts o runPhase0.ts

Crea una variante del load dei task container che:

prende da daily_containers

esclude i task che sono già in daily_assignments_current (per quella workDate)

Questo evita:

duplicazioni

riassegnazioni involontarie di EO/HP già committati

ATTENZIONE: escludere dai candidati ≠ non vederli.
Li vedi tramite loadTimelineBaseline.

C3) Phase 0: passa la baseline in giro (o mettila nel contesto run)

Dove: server/services/optimizer/runPhase0.ts (o dove costruisci il “context” del run)

carica baseline con loadTimelineBaseline(workDate)

carica candidati con loadTasksExcludingAssigned(workDate)

salva baseline in un oggetto “OptimizerContext” passato alle fasi successive

Obiettivo: Phase3 deve avere accesso alla baseline.

D) Phase 3 (Scheduling): costruire assegnazioni intelligenti “attorno” alla timeline

Qui fai il salto vero: HP/LP si adattano anche se EO è stato modificato manualmente.

D1) Inizializza ogni cleaner con route già esistente

Dove: server/services/optimizer/runPhase3.ts

Per ogni cleaner:

se ha baseline:

currentTime = end_time dell’ultimo task in timeline

previousTask = ultimo task in timeline (posizione reale)

altrimenti:

currentTime = start_time del cleaner

previousTask = null (o home)

Quando scheduli un task HP/LP:

usi simulateSequence(..., previousTask) già esistente (o equivalente)

travel e punteggio vengono calcolati in modo coerente perché previousTask è reale, non quello “previsto” dal run iniziale.

Risultato pratico

Se tu sposti EO manualmente:

cambia l’ultimo task/posizione/orari del cleaner

la run HP riparte da lì

HP viene assegnato in modo “intelligente” in base alla nuova realtà

D2) (Step successivo, opzionale) Inserimento nei gap

Se vuoi “intelligente” al 100%:

la baseline non è solo “ultimo task”, ma una sequenza di segmenti

HP può essere inserito tra due task baseline se c’è tempo

(questo richiede più lavoro, ma la struttura è la stessa)

Io consiglio:

prima “append in coda” (già risolve il tuo problema principale)

poi “gap insertion” come miglioramento.

E) Phase 4/score: penalità e straordinarie restano corrette

Non devi cambiare la logica EO/HP/LP nel punteggio: l’hai già.
Con baseline piena, il punteggio cambia naturalmente perché:

i tempi e travel partono da un contesto reale

la penalità di “finire tardi” per EO/HP/LP si applica ai nuovi task schedulati

le straordinarie (che hai modificato) funzionano meglio perché il carico giornata è realistico

F) Flow operativo finale (come lo userete)
1) Run generale per EO (o run-all completo, ma poi applichi solo EO)

POST /api/optimizer/run-all (o la tua run attuale)

in UI vedi proposte EO/HP/LP nei containers

2) “Assegna EO”

apply-wave(EO) → scrive EO in daily_assignments_current

3) Eventuali modifiche manuali

drag&drop → aggiorna daily_assignments_current

4) Run HP “aware”

rilanci optimizer (run-all oppure run HP)

ma ora:

baseline = timeline reale (EO + manual)

candidati = task non ancora in timeline

ottieni un nuovo runId con proposte HP aggiornate

5) “Assegna HP”

apply-wave(HP) → aggiunge HP senza toccare ciò che c’è già

6) Ripeti per LP

run LP aware → apply-wave(LP)
