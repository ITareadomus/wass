🔍 Causa reale del bug

Nel file:

client/src/components/timeline/timeline-view.tsx


la funzione che decide se un task viola la finestra temporale è questa:

const isPriorityWindowViolation = (task: any): boolean => {
  const priority = task.priority;
  const startTimeStr = task.start_time;

  if (!priority || !startTimeStr) return false;

  ...

  if (priority === 'early_out') {
    return startMinutes < EO_START || startMinutes > EO_END;
  } else if (priority === 'high_priority') {
    return startMinutes < HP_START || startMinutes > HP_END;
  } else if (priority === 'low_priority') {
    return startMinutes < LP_START;
  }

  return false;
};

❌ Il problema

Nel resto dell’app (drag & drop, container, task card, ecc.) le priority usate sono:

early-out
high
low


(esempio reale trovato):

currentContainer?: 'early-out' | 'high' | 'low'


👉 Ma qui stai confrontando con:

early_out
high_priority
low_priority


📛 Mismatch di stringhe → la funzione ritorna sempre false → niente classe CSS → niente lampeggio arancione

🎨 Perché il CSS è corretto

Il CSS funziona ed è già definito:

@keyframes blink-orange {
  0%, 100% { border-color: transparent; }
  50% { border-color: orange; }
}

.animate-blink-orange {
  animation: blink-orange 1.5s ease-in-out infinite;
}


E viene applicato correttamente in TaskCard:

${isPriorityWindowViolation && isInTimeline ? "animate-blink-orange" : ""}


👉 quindi il problema NON è grafico, ma logico.

✅ Fix corretto (consigliato)

Allinea i valori di priority.

🔧 Soluzione 1 — Fix diretto (più veloce)
if (priority === 'early-out') {
  return startMinutes < EO_START || startMinutes > EO_END;
} else if (priority === 'high') {
  return startMinutes < HP_START || startMinutes > HP_END;
} else if (priority === 'low') {
  return startMinutes < LP_START;
}

🧠 Soluzione 2 — Normalizzazione (più robusta)
const normalizedPriority = priority
  .replace('_', '-')
  .replace('high-priority', 'high')
  .replace('low-priority', 'low');

if (normalizedPriority === 'early-out') { ... }
