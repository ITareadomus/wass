OBIETTIVO
Ho task “non assegnati” che vivono nei DAILY CONTAINERS. Quando un task viene assegnato/trascinato, passa in TIMELINE.
Se un task è LOCKED, NON deve essere assegnabile, quindi NON deve mai finire in timeline: deve rimanere nei containers.

Problemi attuali:
- Il lock si perde al refresh perché viene salvato su un DB diverso da quello da cui carico i containers
- Il lock non è “hard”: con multi-select o bottone “Assegna” si riesce ancora ad assegnare

Voglio fix robusto:
A) Persistenza lock (refresh-safe) per i task nei containers
B) Blocco UI: non devo poter spostare/assegnare task locked (drag singolo, multi-select/batch, bottone “Assegna”)
C) Blocco backend: nessuna assegnazione deve riuscire se task locked (anche chiamata API manuale)
D) Locked tasks devono restare SOLO nei containers (mai in timeline)

======================================================================
A) BACKEND (Postgres): tabella lock dedicata (source of truth)
1) Crea/assicurati tabella:
   daily_task_locks
   - work_date DATE NOT NULL
   - task_id TEXT/UUID/INT (usa lo stesso tipo usato nel progetto per identificare una task)
   - locked BOOLEAN NOT NULL DEFAULT TRUE
   - locked_reason TEXT NULL
   - updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
   PRIMARY KEY (work_date, task_id)

SQL:
CREATE TABLE IF NOT EXISTS daily_task_locks (
  work_date DATE NOT NULL,
  task_id TEXT NOT NULL,
  locked BOOLEAN NOT NULL DEFAULT TRUE,
  locked_reason TEXT,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (work_date, task_id)
);

2) Nel service Postgres che gestisce lock/containers (es. pg-daily-assignments-service.ts o equivalente):
   - ensureTaskLocksTable(): esegue la CREATE TABLE IF NOT EXISTS
   - getLocksMap(work_date): ritorna map { [task_id]: {locked, locked_reason} }
   - getTaskLock(work_date, task_id): ritorna record lock o null
   - updateTaskLockStatus(work_date, task_id, locked, locked_reason):
       UPSERT su daily_task_locks:
       INSERT ... ON CONFLICT (work_date, task_id)
       DO UPDATE SET locked=EXCLUDED.locked, locked_reason=EXCLUDED.locked_reason, updated_at=now();

3) Modifica loadContainers(work_date):
   - carica i containers come fai già
   - poi applica locksMap SOLO ai task dei containers:
       task.locked = locksMap[task.id]?.locked ?? false
       task.locked_reason = locksMap[task.id]?.locked_reason ?? null

NOTA IMPORTANTE:
Non toccare loadTimeline per aggiungere locked: un task locked non deve andare in timeline, quindi timeline non deve contenere tasks locked.

4) Bootstrap:
   - all’avvio server, chiama ensureTaskLocksTable() (insieme alle altre ensure table).

======================================================================
B) BACKEND: Enforcement (blocco assegnazione)
Devi bloccare TUTTE le vie di assegnazione/move verso timeline.

1) Identifica endpoint usati da:
   - drag & drop (assegna task a un cleaner / timeline)
   - bottone “Assegna”
   - batch/multi-select (se esiste endpoint dedicato)

Esempio endpoint: POST /api/save-timeline-assignment (o simile)

2) In OGNI endpoint che salva un’assegnazione o sposta task da containers -> timeline:
   - prima di fare update:
     const lock = await getTaskLock(work_date, task_id)
     if (lock?.locked) return res.status(423).json({
       error: "TASK_LOCKED",
       message: "Task bloccata: impossibile assegnare",
       locked_reason: lock.locked_reason
     })
   - se locked, NON deve cambiare nulla nel DB / stato.

Così anche se la UI fosse bucabile, non si può assegnare.

======================================================================
C) FRONTEND: Blocco UI totale
1) Drag singolo (onDragEnd):
   - se la task trascinata è locked:
     - annulla l’operazione
     - non chiamare API
     - toast: “Task bloccata: non puoi assegnarla” + reason se presente

2) Multi-select / batch:
   - se stai assegnando un set di task:
     - filtra ed ESCLUDI quelle locked prima di qualunque API call
     - se tutte locked: annulla con toast
     - se alcune locked: procedi solo con sbloccate e avvisa che alcune sono state ignorate

3) Bottone “Assegna”:
   - se task selezionata è locked:
     - disabilita bottone o blocca click
     - non chiamare API
     - toast con reason

4) Gestione errore 423:
   - se qualunque chiamata di assegnazione riceve 423:
     - mostra toast “Task bloccata”
     - non fare update ottimistici
     - non spostare task in timeline

======================================================================
D) CHECKLIST TEST
- Lock un task nei containers con reason
- Refresh: deve rimanere locked + reason nei containers
- Prova drag: non si sposta
- Prova multi-select: non viene assegnato (non finisce in timeline)
- Prova bottone Assegna: non assegna
- Prova chiamata API manuale: ritorna 423
- Timeline NON deve mai contenere tasks locked
