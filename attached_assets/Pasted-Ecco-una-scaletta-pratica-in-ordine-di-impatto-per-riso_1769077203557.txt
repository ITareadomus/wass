Ecco una scaletta pratica (in ordine di impatto) per risolvere:

straordinarie non assegnate

molti task non assegnati

niente gruppi singoli (tranne OT)

0) Prima di tutto: metrica e logging (1 volta sola)

Aggiungi contatori finali per run:

total_tasks, assigned_tasks, unassigned_tasks

ot_total, ot_assigned, ot_unassigned

unassigned_by_reason (es. nessun cleaner compatibile, finestra, max ore, ecc.)

Logga per ogni OT non assegnata: perché (top 1 reason) e lista cleaner compatibili (se 0 → problema dati/regole, non scoring).

Obiettivo: distinguere “impossibile” da “optimizer miope”.

1) Straordinarie: garantire che NON vengano scartate per forma del gruppo
1.1 Fix logico: mai “reject + break” su gruppi OT > 1

Se un gruppo contiene OT e ha size > 2:

non scartarlo subito

droppa task finché diventa valido (OT sola, oppure OT + 1 task ≤2h se OT <4h)

Regola: OT groups devono arrivare in Phase 2 in una forma valida (1–2 task), non essere buttati via.

1.2 Phase 2 selection: OT-first davvero

Ordina i candidati con priorità:

gruppi che contengono OT

gruppi con task “scarcity” (vedi punto 2)

score

Obiettivo: OT non deve arrivare “quando i cleaner sono già pieni”.

1.3 Phase 4: assegnazione OT con swap abilitato

In Phase 4:

assegna prima le OT non assegnate

se nessun cleaner ha spazio, prova swap:

rimuovi 1 task “debole” dal cleaner per farci stare l’OT

accetta se penalty_avoided(OT) > loss_score

Obiettivo: se OT è assegnabile, deve finire assegnata anche sacrificando qualcosa.

2) Tanti task non assegnati: coverage-first con “scarcity” + repair
2.1 Calcola “scarcity” per task

Per ogni task:

compatible_cleaners_count (quanti cleaner lo possono fare rispettando hard constraints base)

più è basso, più è “raro”.

Crea un peso:

scarcity_weight = 1 / (count + 1) o ranking per bucket (0,1–2,3–5,6+)

2.2 Phase 2: non solo score, ma “rarità prima”

Ordina gruppi per:

min(compatible_cleaners_count) tra i task del gruppo (più raro prima)

poi score

Effetto: smetti di riempire con i task “facili” e inizi a coprire quelli “difficili”.

2.3 Phase 4: repair step serio (swap per tutti, non solo OT)

Per ogni task non assegnato (ordine: OT, poi rarity, poi il resto):

prova inserimento diretto

se fallisce, prova swap:

sostituisci 1 task (o 1 gruppo) a minor valore

accetta se penalty_avoided(task) > loss_score

Qui la tua UNASSIGNED_PENALTY diventa finalmente “reale”.

2.4 Penalità unassigned: base + extra

BASE_UNASSIGNED per tutti i task

OT_EXTRA per straordinarie

(opzionale) RARITY_EXTRA per task con pochi compatibili

Obiettivo: minimizzare scoperti in modo coerente con le priorità operative.

3) Mai gruppi singoli (eccetto straordinarie): filtro in Phase 1 + fallback controllato
3.1 Phase 1: filtra gruppi candidati

mantieni solo gruppi con size >= 2

eccezione: gruppi che contengono OT possono essere size 1–2

3.2 Evita di “perdere copertura” per colpa del filtro

Aggiungi una singola eccezione “anti-buco” (facoltativa ma utile):

se un task è rarissimo (es. compatible_cleaners_count ≤ 1 o ≤2),

permetti un gruppo singolo solo come candidato di emergenza

oppure affidalo direttamente a Phase 4 (che però deve fare swap).

Se vuoi essere rigoroso (“mai singoli”), allora Phase 4 deve essere ancora più forte.

3.3 Phase 4: assegnazione singoli come regola, non come scarto

Phase 4 diventa il posto naturale per assegnare singoli

ma con priorità e swap (altrimenti si accumulano unassigned)

Ordine di implementazione consigliato (per vedere risultati subito)

Fix OT group handling (niente reject/break, droppare fino a valido)

OT-first in Phase 2

Phase 4 OT + swap

Scarcity ranking (task + gruppi)

Phase 4 swap per tutti

Filtro “no gruppi singoli” in Phase 1 (+ eccezione OT)
