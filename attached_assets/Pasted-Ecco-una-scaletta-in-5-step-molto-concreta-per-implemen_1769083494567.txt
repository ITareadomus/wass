Ecco una scaletta in 5 step (molto concreta) per implementare relaxLevel + retry + penalty esponenziale estendendo l’attuale Phase 4, senza riscrivere l’optimizer.

1) Introdurre relaxLevel e separare HARD vs SOFT

Dove: server/services/optimizer/phase4.ts (e i helper che usi per feasibility)

Cosa fare

Aggiungi a Phase4Params:

maxRelaxLevel: number

baseRelaxPenalty: number

relaxMultiplier: number

maxAttemptsPerTask: number

maxCleanersToTryPerTask: number

Definisci una funzione unica:

function relaxPenalty(level: number, p: Phase4Params) {
  return p.baseRelaxPenalty * Math.pow(p.relaxMultiplier, level);
}

HARD (mai violare)

compatibilità cleaner↔task (premium, canDoStraordinaria, contract/type_apt se hard)

locked intoccabili

“fisica” (durate, no overlap impossibili)

SOFT (rilassabili per level)

finestre/priority windows / lateness

max load / dynamicMaxLoad (se vuoi 0 unassigned, deve diventare rilassabile almeno a un livello)

travel/wait thresholds

2) Rendere la feasibility “dipendente dal livello”

Dove: le funzioni che oggi decidono se un candidate schedule è valido (quelle chiamate da tryInsertTask / simulazione)

Cosa fare

Crea un wrapper tipo:

function isFeasible(schedule, relaxLevel, params) { ... }


Scala consigliata (semplice):

L0 (strict): come oggi

L1: consenti lateness/priority window violation (penalty alta)

L2: consenti superare max load / dynamicMaxLoad entro un limite (penalty più alta)

L3: consenti travel/wait “alto” (penalty ancora più alta)

L4 (last resort, opzionale): quasi tutto soft violabile (hard ok), penalty enorme

Nota: in pratica non devi “permettere tutto”; basta che non bocci il candidato e invece lo penalizzi.

3) Retry loop per livello: Phase 4 “coverage loop”

Dove: dentro phase4.ts, nell’entrypoint che processa unassignedTasks

Cosa fare

Trasforma Phase 4 in:

remaining = unassignedTasks (non locked)

per level = 0..maxRelaxLevel:

prova ad assegnare solo remaining usando inserimento + swap

ciò che non riesci ad assegnare resta in remaining

se remaining non diminuisce → break (pruning)

Questo ti dà copertura progressiva senza rifare tutto.

4) Modificare scoring: il relax deve “dominare”

Dove: dove calcoli totalScore del candidato in insert/swap (in tryInsertTask e in swap)

Cosa fare

Ogni candidato “valido” al livello L deve includere:

costo normale (travel, lateness, ecc.)

+ relaxPenalty(L)

Quindi tra due soluzioni entrambe assegnanti:

vince sempre quella col livello più basso

e a parità di livello, quella col costo minore

Regola importantissima

Imposta i pesi in modo che sia vero:

UNASSIGNED_PENALTY > relaxPenalty(maxRelaxLevel)

così il sistema preferirà sempre “assegnare con relax alto” piuttosto che lasciare fuori.

5) Swap “vero” con re-enqueue + cap performance

Dove: trySwapForTask / logica swap in phase4.ts

5A) Re-enqueue obbligatorio

Quando fai swap (1-out-1-in):

il task rimosso non deve diventare “remain_unassigned” definitivo

deve tornare in coda remaining (magari allo stesso relaxLevel o al successivo)

Altrimenti non stai minimizzando unassigned, stai solo “scambiando”.

5B) Cap per performance

Per ogni task in un dato livello:

prova al massimo maxCleanersToTryPerTask cleaners (selezionati con euristica veloce)

e massimo maxAttemptsPerTask tentativi complessivi (tra insert posizioni + swap candidates)

Euristica veloce per scegliere i top cleaners:

compatibili hard ✅

ordina per “distanza stimata” dal punto migliore (inizio/fine o nearest task) e prendi i primi N

Cosa ottieni con questi 5 step

Se un task è assegnabile sotto HARD: Phase 4 lo assegna prima con L0, poi rilassa solo se serve.

Le “scelte brutte” compaiono solo quando indispensabili.

Tra le brutte, sceglie le migliori perché minimizza: livello → costo totale.

Unassigned finali = solo locked + eventuali “impossibili HARD” (0 cleaners compatibili).
